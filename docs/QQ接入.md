# 普通 QQ 号接入（OneBot 11 / NapCat）

当前默认入口已改为普通 QQ 号。NapCat 负责登录与 QQ 协议收发，本项目使用 NoneBot OneBot 11 适配器，主动连接 NapCat 的本机正向 WebSocket；不新增服务监听端口。本服务器已完成 NapCat 部署、扫码登录及用户确认的真实收发。

## 配置与启动

1. 在运行本项目的同一主机部署 NapCat，登录专用测试 QQ 号（登录由你完成，密码不交给项目）。若在个人电脑运行 NapCat，需先通过 SSH 隧道把该机的 WebSocket 端口转发为服务器本机端口。
2. NapCat 网络配置中开启 **WebSocket 服务端（正向 WS）**，地址绑定 `127.0.0.1`，例如端口 `6700`；设置强随机 token，消息上报格式选择 **array**。容器场景需只向主机回环地址映射端口。
3. 项目 `.env` 填 `AVATAR_ONEBOT_QQ`（登录 QQ 号）、`AVATAR_ONEBOT_TOKEN`（同一 token）、`AVATAR_ONEBOT_WS_URL=ws://127.0.0.1:6700`。无需官方 AppID/AppSecret。不要将密钥写入 URL 或聊天。
4. 在项目独立虚拟环境安装 `requirements-qq.txt`（或项目的 `qq` extra）。现有服务器的可选依赖隔离在 `/data/Users/zyyh/runtime/qq-deps`，启动脚本自动加载，不需要重装核心环境。
5. `./scripts/qq.sh --check` 检查本地配置与 SDK；`./scripts/qq.sh --smoke` 做离线 OneBot 消息归一化、去重和假发送演练；`./scripts/qq.sh --run` 才连接 NapCat。检查与演练不联网，也不判断账号实际在线。

本机正向 WS 配置参考 [NoneBot 官方文档](https://onebot.adapters.nonebot.dev/docs/guide/setup/) 和 [NapCat 接入文档](https://doc.napneko.icu/use/integration)。非官方 QQ 客户端接入可能导致账号受限，先用专门测试号。

## 当前收发边界

- 仅好友私聊、群内明确 @ 本账号的纯文本。忽略自己的消息、普通群消息、空 @、图片、语音、文件、合并转发及临时私聊；不自动通过好友/入群申请，不主动发消息。消息必须使用数组格式，群内同时 @ 其他账号的混合消息也暂不处理。
- SDK 会预处理并删除 @；本接口从 SDK 保存的原始消息校验 @，不依赖可被用户仿造的字符串。拒绝其他登录账号的事件。
- 回复用明确的纯文本消息段发送，模型生成的 `[CQ:...]` 不会执行为 @、图片或其他动作。收件人只从已校验事件确定。
- 复用 AvatarEngine、SQLite 回执、重复事件抑制、群级持久限流与安静时段。OneBot 账号身份有独立命名空间，默认数据目录 `data/qq-onebot`，不与官方接口或网页共享个人记忆。
- 连接失败由适配器重连；发送结果不确定时保留 `delivery_unknown`，不盲目重发。支持文本接口不代表真实 QQ 已验证。

# QQ 官方机器人接入接口

2026-11-10，第一版文本接口。复用 Avatar 的对话、记忆和情绪能力，通过独立 NoneBot 服务连接 QQ 官方机器人。没有将本机 Mission Control 管理接口暴露给 QQ 或公网。

## 当前能力与范围

- 接收官方 `C2C_MESSAGE_CREATE` 单聊，以及 `GROUP_AT_MESSAGE_CREATE` 群内 @ 消息；普通群消息、频道事件、图片、语音、文件和机器人消息不处理。
- SDK 负责官方鉴权、事件接收和回复发送。应用自身不实现账号密码登录，也不使用 NapCat/OneBot 个人账号协议。
- 上下文按机器人、单聊/群聊、会话目标和发言用户隔离，使用 SHA256 生成存储键；同一人的私聊、不同群和群内其他用户不共享个人记忆、摘要、提醒、情绪或风险路由状态。
- 每个作用域使用独立 SQLite，与网页默认记忆库分开；短期最近 20 条消息和运行状态会恢复。当前不合并跨平台身份，不自动同步网页已保存的人设版本、知识或个人记忆；人设先沿用环境配置。
- 普通陪伴消息使用 `use_web=False`，明确查询请求接入只读工具（见文末）；均关闭 TTS。无从 QQ 执行管理草案或任意选择平台收件人的入口。原有明确文本提醒解析仍只作用于当前隔离上下文，消息体不是管理权限。
- 生产回复绑定收到的 SDK 事件，平台目标由事件决定，模型只返回文本。只做被动回复，没有主动群发或定时推送。

## 消息处理与恢复语义

1. 解析并检查消息类型、发送者、会话目标、消息 ID、正文和带时区时间戳。正文最多 4,000 字符，不下载媒体。
2. 按机器人、事件类型和消息 ID 生成持久化收件键；完整事件指纹不同的同 ID 重放记为 collision，拒绝处理。
3. 同一上下文串行，不同上下文交给有限线程池。默认四个 worker、全局最多 32 个待处理事件、每上下文最多四个，超限记 busy，不无限堆积。
4. 模型/SQLite 工作在线程中执行。收到取消时等待正在运行的线程结束再释放同一上下文锁，防止并行写乱会话。
5. 记忆变更、情绪/风险状态和生成回复缓存放在同一作用域 SQLite 事务中；生成异常回滚。重投递时复用已有回复，不重新产生记忆副作用。
6. 发送前持久化 sending；成功记 sent。发送报错、超时或 sending 状态下重启均记 delivery_unknown，不自动重发。平台调用与本地 SQLite 无法形成同一事务，不承诺端到端 exactly-once。

默认接收最长两分钟内的事件，未来时钟偏差容忍 30 秒；发送前再次检查。排队或模型调用导致过期则不再发送。发送单次等待上限 20 秒；常规模型请求关闭客户端自动重试并设置 30 秒超时，认知分析沿用核心接口的 45 秒超时。单条输出限制 3,000 UTF-8 字节，超过时截短并标明；暂不拆成多条消息。

重启会把未完成的 processing 记录改为可重试生成，把 sending 改为结果不确定。ready 仅在同一事件再次投递时读取回复缓存继续发送，不自动扫描并补发待发送消息。回复缓存缺失记 generation_unknown，不重新生成或猜测收件人。该策略优先避免重复和错发，可能漏发，需要查看本地状态；没有假称网络失败一定未发送。

QQ SDK 内部的官方请求行为遵循它的实现；本应用保证自己的已完成收件事件不重复调用发送器。不同状态目录之间没有分布式去重，因此同一 AppID 应只启动一个实例、使用同一状态目录；目录有进程锁防止误开第二实例。

## 数据与隔离

默认目录：

```text
data/qq/
  service.lock
  receipts.db                         # 指纹、状态与时间，不存完整正文
  contexts/<作用域哈希>/memory.db       # 此作用域的记忆、消息、运行状态和回复缓存
```

此目录受 Git 忽略；在 POSIX 上创建为 0700、数据库 0600。日志只输出处理状态、异常类型和收件哈希前缀，不主动打印消息正文、用户 openid 或 AppSecret。QQ SDK 自身日志仍需按部署环境审阅，避免开启详细调试日志。

群里收到的用户话语不会成为其他人的个人画像。群内对话当前按发言人隔离，因此不提供“通读全群上下文”的能力。前端管理台现有「QQ 会话」页面管理 OneBot 各作用域，见文末。备份或清理前先停止 QQ 服务，按完整状态目录处理；不要只删去重表后继续使用旧会话缓存，也不要把目录提交仓库。

## 发言、表达与上下文预算

仅接收私聊和群内 @，无概率唤醒、主动插话或后台主动发送。群级额度按机器人与群共享，不因换用户而绕过：默认两次新请求间隔至少 2 秒、每分钟 2 次、每小时 20 次。额度在 SQLite 事务中先于生成预留，重启保留；生成或发送失败也保守占用该次额度。重复事件沿用已有回执，不重复扣额度。超额消息本次静默，不排队补发；平台后续重投时可重新判断是否仍新鲜、是否允许接收。

`.env` 的 `AVATAR_QQ_GROUP_COOLDOWN`、`AVATAR_QQ_GROUP_PER_MINUTE`、`AVATAR_QQ_GROUP_PER_HOUR` 可调整额度。`AVATAR_QQ_QUIET_START`/`END` 默认均为 `-1`（关闭）；例如 `23`/`7` 表示 UTC+8 晚上 23 点至早上 7 点不接收新的群内 @ 请求，私聊仍正常回应。已经接收的请求继续完成。配置无效时启动失败，不悄悄采用其他值。

QQ 表达提示复用现有 PAD 与六种回应策略，强化具体任务直接交付、倾听时不安排任务、告别时不另开话题，不增加一套情绪状态；事实、安全边界优先。提示调整尚未证明真实模型体验增益。

上下文使用字符预算（不是精确 tokenizer 计数）：历史最多 4,000 字符，当前输入最多 4,000 字符，完整系统提示最多 16,000 字符。画像、事实、提醒、摘要分别限制序列化字符预算，只保留完整条目；历史保留连续的最近消息，不拼接跨缺口对话。超长条目跳过，仅影响本轮提示，不删除持久记忆。完整安全提示每轮保留，系统提示仍超限则生成失败，不截断安全规则。认知分析也只读取恢复后的有限历史。大人设配置、真实 tokenizer token 数和长对话效果仍需后续实测。

设计参考 deepseek-fish 的发言门控、语境表达及成本预算思路；本次为本项目 Python 实现，未引入其 SnowLuma/DSH 接入或执行其安装脚本。

## 固定回复与模型诊断

如果消息能收发但只有固定回复，先区分 QQ 传输和模型服务：`--check` 中 `credentials_configured` 只说明账号配置完整，`model_configured` 只说明已配置 LLM key，不会联网检查模型健康。检查本地模型进程、端点和服务日志。QQ 遇到未配置模型或模型生成失败时现在明确返回“我现在暂时无法生成完整回复，请稍后再试。”并记录降级类别，不返回假装正常理解的固定倾听话术。

本服务器当前本地模型为 Qwen3-4B-Q4_K_M，CPU llama.cpp 监听 `127.0.0.1:18081`；配置在本地 `.env`，无云端调用。QQ、模型与 NapCat 的 PID/日志分别保存在 `/data/Users/zyyh/runtime/napcat/state` 与 `logs`。目前为后台进程，重启服务器后需要恢复服务，不具备开机自启。已有旧固定回复保留在历史中，新事件将使用新模型，不回放旧事件。

## 日常健康检查与优化记录

`./scripts/qq.sh --health` 会实际执行只读探测：验证 OneBot 登录账号/在线状态、读取本机模型 `/models` 确认所配模型存在，以及检查 Avatar 状态目录的实例锁是否被持有。不会发送 QQ 消息或调用模型生成；不探测云端模型，不跟随 HTTP 重定向。全部正常返回退出码 0，否则为 1。它证明本机连接和进程状态，不保证下一轮模型内容正确。原 `--check` / `--smoke` 仍离线运行。

QQ 系统提示改为固定身份与安全规则在前、每轮变化的策略提示在后，让本地推理服务器更容易复用提示前缀；未省略或隔轮注入边界规则。网页/CLI 默认提示顺序保持原状。本轮表达提示试验尝试强调发信人视角、已知事实与自然收尾，但真实开发对话仍有视角错误和用承诺代替成稿的问题，未证明稳定增益，未部署这部分试验；现有表达提示保留。

QQ 上下文库新增 `qq_turn_metrics`，最多保留最近 1,000 次真实引擎生成的总耗时、分析耗时和回复降级标志；不在指标表中保存聊天正文、账号或凭据。缓存回放不重复计为模型生成。`qq_degraded_messages` 标记故障回复，恢复上下文时排除；早期两种已知固定故障话术也从助手历史恢复中排除。原聊天审计、有效用户事实和事件回执保留，不删除记忆。

## 后台与 QQ 的已接通能力

管理台新增 `/qq`「QQ 会话」页。只在已有本机管理令牌鉴权后提供会话列表、记忆详情与来源、纠错/误召回/彻底删除草案、确认执行、该会话审计和最近 50 条处理记录。确认令牌绑定对应会话库，跨会话不能复用；个人记忆不合并进后台主库。会话正在处理消息时数据库可能繁忙，稍后刷新重试。旧会话先显示摘要编号，收到新消息后补全账号/群标签。当前页面管理普通号 OneBot 状态目录。

QQ 每轮只读后台 `AVATAR_QQ_ADMIN_DB`（默认 `MEMORY_DB_PATH`）的**已确认人设版本和相关知识**；草案不生效。全局人设/知识确认后下一条新消息生效，已经生成或发送的回复不自动重做。后台个人记忆、聊天原文、提醒、确认令牌不共享给 QQ。**知识与人设属于面向 QQ 的共享配置，导入前确认内容适合向 QQ 用户提供。** 当前生产知识库还没有导入来源，需要在「知识与学习」导入并确认后使用。

记忆纠错在「QQ 会话」中选定用户/群后执行：预览差异→确认→检查该会话审计。下一轮从数据库重新恢复事实，不依赖旧进程缓存。管理 API 不开放给 QQ 聊天；收到“修改人设”“清空所有用户”等消息不会获得管理权限。
