# Mission Control 数字人大脑后台设计

## 1. 意图

把现有“记忆工作台”升级为项目长期使用的专业 AI 控制台。后台不只是查看工具，而是数字人大脑的可解释管理面：管理员能够观察对话决策，调整人设和情绪，纠正记忆，导入知识，并通过自然语言生成管理操作。

所有可能改变大脑状态的自然语言管理和批量操作必须经过：

`生成草案 → 展示字段级差异和影响范围 → 管理员明确确认 → 事务执行 → 写入审计记录`

人设、情绪、知识修改一律不得自动生效。

## 2. 目标

- 使用 React + TypeScript 构建可长期扩展的 Mission Control 风格后台。
- 保留 Python 作为唯一业务后端和安全边界，前端不直接操作 SQLite。
- 支持总览、对话观测、人设、情绪、记忆、知识、提醒、工具和审计模块。
- 所有写操作有结构化预览、明确确认、原子执行和可追踪结果。
- 正式演示仍由一个 Python 启动入口提供 API 与前端构建产物。
- 保持单用户、本机 `127.0.0.1` 使用范围，不伪装成多人权限系统。

## 3. 非目标

- 本阶段不实现多人账号、RBAC、远程公网部署或云端控制台。
- 不在后台直接训练模型；只为未来训练数据和评测管理预留导航位置。
- 暂存已确定的训练路线：100 条锁定评测集、约 1,000 条自动筛选训练数据、4B LoRA SFT/DPO、OPD 后置；本阶段不调用云端 API 批量生成数据。
- 不让管理 Agent 自由执行 SQL、文件命令或任意工具调用。
- 不用大模型裁定数据库事实；事实约束仍由现有记忆版本、Guard 和 Verifier 负责。
- 不改变 ASR、TTS、口型和渲染链路。

## 4. 已选方案与备选方案

### 已选：React 独立前端 + Python REST API

前端使用 React、TypeScript、Vite、React Router、TanStack Query、Tailwind CSS、Recharts 和 Lucide。开发期运行 Vite；生产构建输出到 `frontend/dist`，由 Python 服务托管。

选择原因：后台已经发展为多模块、复杂表单、差异预览、图表和审计系统，原生单文件 JS 会让组件复用、状态同步和测试成本持续上升。

### 未选：继续扩展单文件 `web_ui.py`

优点是零构建、改动快；缺点是复杂交互和页面状态难以维护，只适合小型本机工具。

### 未选：模块化原生 HTML/CSS/JS

能保留零 Node 依赖，但仍需自建组件、路由、缓存和表单状态。随着管理能力增加，长期成本高于 React。

## 5. 信息架构

### 5.1 总览

- 顶部显示后端、模型、Ollama、数据库和工具服务状态。
- 指标只展示真实数据：当前记忆数、情绪状态、最近验证通过率、工具健康度。
- “数字人大脑状态”汇总人格版本、策略、上下文、Guard/Verifier 状态。
- 最近认知事件来自审计与对话事件，不生成装饰性假数据。

### 5.2 对话观测

- 聊天气泡与现有对话入口。
- 每轮显示召回记忆、情绪判断、响应策略、工具调用、Guard 和 Verifier 结果。
- 调试信息默认折叠，不污染正常对话阅读。

### 5.3 人设管理

- 编辑角色名称、核心定位、表达原则、关系边界和不可覆盖规则。
- 每次修改创建不可变版本；当前版本只通过确认操作切换。
- 提供旧值/新值字段差异、测试对话预览和回滚入口。
- 人设版本进入 `Avatar` 提示词，现有环境变量作为首次迁移默认值。

### 5.4 情绪干预

- 展示角色 PAD 状态、用户最近情绪、活跃度和近期趋势。
- 手动干预是有持续时间的覆盖层，不直接篡改历史观测。
- 草案包含目标值、持续时间、原因和恢复策略；到期后恢复自动状态更新。

### 5.5 记忆中枢

- 保留现有搜索/列表、来源、历史、纠错、删除和不相关反馈。
- 增加类型、状态、确认状态和时间筛选，以及批量操作草案。
- 纠错保留历史链；彻底删除继续使用明确危险确认。

### 5.6 知识与学习

- 第一阶段支持粘贴文本与选择本机允许目录中的 UTF-8 文本/Markdown 文档。
- 单文件限制 5 MiB，仅接受 `.txt`、`.md` 和 UTF-8；上传使用专用端点，不复用普通 JSON 的 16 KiB 限制。
- 导入先生成切片预览：来源、标题、字符数、切片数、重复项和拒绝原因。
- 确认后才写入独立知识表；知识与用户记忆分开存储和检索。
- 不接受网页 URL 自动学习；联网内容需显式抓取、展示来源后再进入导入草案。

### 5.7 提醒与工具

- 复用现有 SQLite 提醒能力。
- 展示资料、联网、天气和提醒工具健康度、最近调用与错误。
- 工具配置只允许后端白名单字段，不显示或回传密钥。

### 5.8 操作草案与审计

- 自然语言管理入口位于全局命令栏，例如“让小海更克制一些”。
- 管理 Agent 只能输出后端定义的操作类型和 JSON 参数，不能自行增加操作类型。
- 管理 Agent 默认使用当前本地模型；云端模型必须由管理员当次显式选择，后台不得因失败自动产生云端费用。
- 后端验证草案的 schema、当前版本、权限范围和影响对象，返回字段级 diff。
- 确认请求必须携带草案 ID 和一次性确认令牌；过期、已执行或基线版本变化的草案拒绝执行。
- 执行在一个数据库事务内完成，成功或失败都写审计；审计正文不得保存 API key。
- 可逆操作生成反向草案，仍需再次确认；“回滚”不是绕过确认的快捷写入。

## 6. 前端架构

目录建议：

```text
frontend/
  src/
    app/          # 路由、QueryClient、应用壳
    components/   # 导航、状态、差异预览、确认对话框
    features/     # dashboard/chat/persona/emotion/memory/knowledge/audit
    lib/          # API client、类型、格式化
  tests/
  package.json
  vite.config.ts
```

- 使用特性目录，页面、查询和组件就近放置。
- TanStack Query 管理服务端状态；临时表单状态留在对应页面。
- API 类型先手写并由契约测试约束，不在本阶段引入 OpenAPI 代码生成。
- 深色为默认主题，保持专业控制台的高信息密度；移动端支持查看和简单操作，复杂差异确认优先桌面。
- 不从 CDN 加载脚本、字体或图标；生产环境符合现有 CSP。

## 7. 后端架构

### 7.1 API 分层

- `web.py` 只负责 HTTP、安全头、请求验证和静态资源。
- 新增管理服务层，封装人设版本、情绪覆盖、知识导入、草案和审计事务。
- API 使用版本前缀 `/api/v1/`；现有接口在迁移期保留兼容。

### 7.2 数据模型

- `persona_versions`：不可变人设版本、父版本、状态、创建时间。
- `emotion_overrides`：目标 PAD、开始/结束时间、原因、状态。
- `knowledge_sources` / `knowledge_chunks`：来源与切片，和记忆表分离。
- `operation_drafts`：操作类型、参数、基线版本、diff、过期时间和状态。
- `audit_events`：操作、目标、结果、前后版本引用、时间和错误摘要。

迁移必须幂等，旧数据库可直接升级。现有人设配置在首次启动时迁移成初始版本。

### 7.3 安全边界

- 继续只监听 `127.0.0.1`，保留随机 token、Host/Origin 校验、CSP、请求大小限制和 `no-store`。
- 前端构建产物使用固定路径映射，禁止任意文件读取和目录遍历。
- API 不返回 `.env`、模型密钥、代理凭据或完整异常堆栈。
- Markdown/知识内容按纯文本展示；不得注入 `innerHTML`。
- 危险写入使用草案确认令牌和乐观并发版本，避免旧预览执行到新状态。

## 8. 核心流程

### 自然语言人设调整

1. 管理员输入自然语言要求。
2. 后端调用管理 Agent，得到白名单操作 JSON。
3. 后端根据当前人设生成结构化草案和 diff。
4. 前端展示影响、测试对话和警告。
5. 管理员明确确认。
6. 后端校验令牌与基线版本，在事务中创建新版本并激活。
7. 写审计事件；前端刷新当前人设。

### 知识导入

1. 上传或粘贴内容。
2. 后端解析、切片、去重并生成预览，不写正式知识表。
3. 前端展示接受/拒绝切片和来源信息。
4. 管理员确认后原子写入来源、切片和审计事件。

## 9. 错误与降级

- 大模型不可用：自然语言管理返回“无法生成草案”，手动结构化编辑仍可使用。
- 草案过期或基线变化：拒绝确认并要求重新预览。
- 知识解析部分失败：预览中逐项显示；默认整批不执行，管理员可生成仅含成功项的新草案。
- 前端构建产物不存在：Python 返回明确安装/构建提示，不回退到不完整旧 UI。
- 审计写入失败：业务事务整体回滚。

## 10. 测试与验收

- Python 单元/集成测试覆盖迁移、草案状态机、令牌、过期、并发冲突、事务回滚和密钥脱敏。
- HTTP 测试覆盖 token、Origin、静态资源路径穿越、请求体限制和兼容 API。
- React 使用 Vitest + Testing Library 覆盖路由、加载/错误/空状态、diff、确认和不可绕过确认流程。
- Playwright 覆盖人设修改、情绪干预、记忆纠错、知识导入四条关键路径。
- 验收要求：任何写操作无法跳过预览和确认；刷新后状态一致；失败不产生半写入；审计可追踪；现有 Python 全量测试继续通过。

## 11. 交付顺序

1. 前端应用壳、生产静态托管和现有功能迁移。
2. 草案/确认/审计基础设施。
3. 人设版本与自然语言管理。
4. 情绪覆盖与趋势。
5. 知识导入与独立检索。
6. 对话观测、工具健康度和整体视觉收尾。

每一阶段必须可运行、可测试、可独立提交；不得等全部功能完成后一次性集成。
