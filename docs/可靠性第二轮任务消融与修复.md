2026-11-09。承接[第一轮开发回归](可靠性第一轮开发回归.md)，本轮只研究事实提示、任务状态和交付检查，

GPU使用同一NUMA组的0–3号空闲卡，最多同时4张，任务无墙钟截断。
默认组复用第一轮安全V3的111条固定回复；本轮四个实验组均重新运行。

AI重点内容审阅发现：

- 事实提示修正旧lora-dev-03末轮遗漏的“甲负责通知”，但旧lora-dev-05仍把“收到两人回复”编成“确认参加”。

- rel-27任务状态单开就编出“今天下午、紧急工作、无法到岗”，表明去掉事实提示也不能保证不编造。
- rel-20算术错误未解决，仍可能把10+20+25说成35分钟；旧lora-dev-17排他约定也仍未解决。

这些证据不足以默认启用任一实验提示。

## 任务状态工程修复

通过独立受控测试确认并修复：

1. 保留/删除按各自分句及就近操作解析；支持同句多个操作、操作在占位符后，以及后续恢复。
2. 新增禁止保留的占位符记录，检查删除是否实际生效，不再只有“必须出现”一种检查。
3. “写取消订单的消息”与“取消这个任务”分开处理。
4. 支持明确的“姐姐让我替她”“起草姐姐的回复”和物业收件人；代词修订保留已知委托人。
5. 用户转为只想倾诉时清空旧写作任务。
6. 明确“留作/留为”的未知值占位也必须保留。

主体抽取只是支持明确表达的保守规则，不是通用角色理解器。
中间澄清消息仍可能清空任务，生成器也仍可能混淆委托人与当事人，不能将这两类问题标成已全部修复。

增加[10条任务修订开发场景](../evals/companion/task-revision-dev-10.json)，共20用户回合。
这些由实现者知晓代码后编写，不是独立验收集，不允许进入训练。
原30条与旧20条不改动，修复版对60场景131轮分别运行任务状态单开和任务状态加检查。
新10条另跑默认组及修复前任务+检查组，供相同用户输入对照。
V2是中间诊断，V3补齐“留作/留为”后重新完整运行，最终结论只使用V3。

## 检查与内容质量的区别

一次修正最多调用一次回复模型，失败保留原稿及未解决问题记录。
`repair_succeeded`只表示现有窄检查不再报错，不等于语义、事实或任务整体通过。

已经观察到的反例：task-rev-07缺少通知具体内容，修正后虽然没有被删除的地点占位、保留了时间占位，
却写成“【时间】请准时参加”，增加了未提供的参会事件；不能算可靠交付。
task-rev-03还会将“用户读数正常”改成“隔壁读数正常”，并在一次修正后仍丢失【房号】。
旧lora-dev-07即便保留【房号】，仍可能把姐姐的卡失效和用户的卡正常混为同一人的陈述。
任务状态字段正确、格式检查成功，均不能代替最终内容审查。

新task-rev-02的“取消订单消息”对请求取消还是已取消通知存在意图歧义；它能检验任务是否被误取消，
但不能仅凭拟写的“已取消”文案断言工具被实际执行，后续语义验收需澄清任务意图。
通知和邮件未给出具体事由时，合理澄清或留空不应一概判为未交付。
