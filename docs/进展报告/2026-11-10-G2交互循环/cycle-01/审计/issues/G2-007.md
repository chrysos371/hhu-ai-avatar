# G2-007：持久助手派生文本未随来源删除

优先级：P1。状态：已修复，专项与原探针复测通过。

## 现状与实验数据

在隔离数据库发送“我叫审计专用甲”，生成完整回复，再删除名字记忆。运行缓存现已清除，但直接查询 SQLite 的助手消息，仍包含“审计专用甲”。[实际探针结果](../evidence/audit-after-core-fixes.json) 中 `persisted_assistant_contains_erased_name=true`。

## 审计结论

已有删除逻辑遮蔽用户来源原文，却没有记录助手回复用了哪些事实/原话，因此不能同步清理持久派生内容。只清缓存不能解决这个问题。

## 优化目标与复测

记录回复使用的事实与用户来源；删除来源时清理派生助手副本，旧库中无法追踪的助手内容采用明确的保守清理策略。生成期间发生删除时，提交前检查上下文版本并原子化写入，防止重新写回旧内容。验证跨会话召回、旧库、取消/删除竞争、回滚和未相关内容保留。

## 修复与验证

- 新增仅保存 ID 的回复来源关系，覆盖引用的画像/事实、当前会话输入、前文助手内容和摘要来源；删除时递归清理跨回复派生链。新记录中明确无关联的回复保留。
- 对无法追踪来源的旧助手记录保守脱敏，并在管理删除预览说明范围；不将旧数据伪装成已有精确来源。
- 用户消息、最终助手消息与来源写入保持事务边界，生成前快照与提交时版本检查置于同一写事务；生成过程中外部删除会阻止旧内容持久化。
- 补齐“仅删除摘要原话、没有关联事实”的路径；回复和来源记录可共同回滚。
- 来源清理/摘要/管理专项 **21 passed**；此前来源/主流程/旧库专项 **78 passed**（有重叠）。[同探针复测](../evidence/audit-after-lineage.json) 中持久助手包含名字 **true → false**，缓存和事件也仍不可读；并发读 160 次无失败。
