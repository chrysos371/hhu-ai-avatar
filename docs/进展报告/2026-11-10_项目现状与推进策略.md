# 项目现状与推进策略

> 调研日期：2026-11-10
> 范围：仓库代码、项目说明、后端设计、陪伴评测与路线图。此报告是基于仓库现有材料的案头调研，没有重新运行全量测试或真实模型评测。

## 摘要

项目已从最初的“语音虚拟形象原型”发展成以文本陪伴为主、具备版本化记忆、情绪策略、边界控制、本机管理界面和可选工具的交互后端，并建立了可复现的场景评测管线。当前的主要瓶颈不是缺少新模块，而是**还没有冻结可信的正式评测标准，也没有人工复核关键行为结果**。已有实验显示，事实存储和部分边界路由能工作，但模型仍会出现任务视角错误、具体任务交付失败、模板化表达、现实边界遗漏等问题。

建议按“评测可信度 → 可复现缺陷与行为质量 → 有门槛的数据训练 → 演示链路与部署”的顺序推进。暂不扩大训练数据规模，不进入 OPD，也不把语音/渲染接入包装成核心智能能力的进步。

## 一、当前项目状态

### 1. 产品与架构

项目定位是河海大学大创的 AI 虚拟形象底座，参考 AIRI 的思路用 Python 实现。核心编排位于 `src/avatar/main.py`，连接事实分析、记忆、用户/角色情绪、回应策略、边界策略、LLM、摘要、提醒和可选工具。

当前代码包含约 3,736 行 Python（按 `src/avatar` 文件统计）和 34 个测试文件。主要能力如下：

| 子系统 | 当前实现 | 现阶段限制 |
|---|---|---|
| 对话与认知 | OpenAI 兼容 LLM；分析与普通回复分开；分析支持结构化 JSON Schema | 模型服务支持、推理格式遵循和响应质量仍会影响可用性；异常时会回退，需把降级作为结果的一部分看待 |
| 记忆 | SQLite；短期窗口、事实版本、来源证据、纠错/删除、摘要、关键词与可选 Ollama 向量混合召回 | 语义召回默认关闭；阈值依赖模型和数据，需要标注样例校准；模型回答是否真正使用召回事实不能只看候选列表 |
| 情绪与策略 | 用户情绪与角色状态分离；包含倾听、澄清、共情、建议、庆祝、回答、收尾等策略 | PAD、意图分类和若干路由仍含规则启发式；策略命中不等于回复质量合格 |
| 边界控制 | 现实/关系/隐私/危险情绪规则与输出检查 | 规则有措辞覆盖面和误触发边界；近轮评测仍发现台词语境过度反应与角色视角错误 |
| 工作台与提醒 | 本机单用户 Web 管理页，支持记忆查看/纠错/删除、反馈、摘要和提醒 | 设计目标为本机单用户；不是多用户权限系统，也没有系统后台推送 |
| 联网与 MCP | 可选网页搜索/读取、天气、授权资料目录和本地提醒工具 | 工具执行的正式隔离评估尚未建立；外部调用成功与回复中的诚实说明需分别验收 |
| 语音与呈现 | FunASR、Edge-TTS、LPC 口型分析模块已存在 | 主体评测以文本为主；ASR/TTS/口型的端到端质量、延迟、真实设备体验尚缺近期证据；Live2D/Godot 未接入 |

### 2. 评测与实验成熟度

- `scripts/evaluate_companion.py` 能运行模型直测、Avatar 集成和离线 smoke；记录原始调用、数据库状态、路由、分析回退、截断、耗时和来源信息。
- `candidate-100.json` 有 100 个候选场景、310 个用户回合，含记忆、情绪、边界三类。但文档明确指出新增 85 条尚未全部审核，候选集包含已参与开发的样例，不能作为盲测或未见正式测试集。
- Qwen3-4B 的 20 条直测与 Avatar 集成对照显示：集成带来部分局部改善，但也出现事实遗漏和分析降级；两种配置同时改变了上下文和后台，不能把差异归因到单个模块。
- 边界开发对照显示规则路由可以按预期工作，但不能据此推出模型自身能力提升。后续 12 条一次性检查的 AI 初审是 6 条满足、5 条部分满足、1 条失败，仍待人工复核；其中明确拒绝后的角色视角错误和最小任务不对应用户任务，是高价值失败证据。
- `docs/陪伴大脑训练路线.md` 已说明正式保留集未冻结、训练尚未开始、OPD 仅为后段路线占位。这个判断与当前证据相符。
- README/AGENTS/旧进度记录存在时间差。`docs/项目进度.md` 有 2026-09 的原型状态；AGENTS 的“当前代码状态”和 README 的部分路线说明也未完全同步。评估时应按文件日期与实现核对，不能把旧条目当当前事实。

### 3. 版本与协作状态

调研开始时工作区干净，`main` 与 `origin/main` 无领先/落后提交；通过 SSH 检查远端，无新提交。当前克隆的 `origin` URL 是 HTTPS，和用户快照中记录的 SSH 约定不一致；本次 fetch 使用了 SSH 临时覆盖，没有改动仓库远端配置。提交前会按用户已提供的版本约定使用指定提交作者，并用 SSH 推送。

## 二、主要判断与风险

1. **最大风险是评测闭环未完成。** 当前有丰富开发证据，却缺少经过人工审阅、隔离良好、预先规定放行门槛的正式保留集。若先训练、再按同一批暴露场景调提示，无法判断泛化提升。
2. **后端正确性与表达质量是两类问题。** 记忆事实被正确写入或边界路由命中，不代表模型表达正确；反过来，回复表面正确也不能证明数据库没有错误或分析没有降级。评测报告必须继续分开统计。
3. **规则继续堆叠会增加维护成本。** 规则适合做可审计的确定性操作、紧急控制流和硬边界；不适合无限承担反讽、语境、邀请者/被邀请者视角、任务意图等开放语义判断。
4. **训练存在数据泄漏和归因风险。** 现有试点、开发集和一次性检查都已对开发过程可见。它们不能直接改名后进入训练再作为验证。训练前还需解决来源、授权、人工审核、场景家族隔离及模型权重/推理参数复现。
5. **产品叙事领先于端到端证据。** 项目说“听→思→演→记”，但近期强证据主要来自文本后端。ASR、TTS、口型和渲染还未形成同等质量的集成验收；项目演示应明确哪些是已测能力、哪些是模块原型。
6. **本机工作台有明确单用户边界。** 在未设计认证、授权隔离和数据隔离前，不应把当前服务当作团队或公网多用户产品部署。

## 三、分优先级推进策略

### P0：建立可信的验收闭环（下一步首选）

目标：先让后续修改能够被可靠判断。

1. 人工复核 `experience-check-12` 的 12 条和现有关键失败；将 AI 初审、人工复核、分歧裁决分开记录。
2. 审核 `candidate-100` 的新增场景，标注歧义、预期行为、关键失败、适用的后台断言与不适用项。
3. 新建按 `scene_family` 隔离的开发集与正式保留集；保留集不参与提示词、规则、训练样本开发。现有暴露集保留作回归集。
4. 在看到正式结果前写定放行标准：按记忆、情绪、边界、工具和表达分别报告；定义 hard failure、降级、错误、截断的处理；关键边界不得由其他维度高分抵消。
5. 对正式结果做至少三次独立运行并报告波动；高风险场景做双人评审或人工裁决。记录模型权重/adapter revision、推理服务版本、参数、源码/样例哈希。

**交付物：** 已审阅的场景清单、隔离清单与哈希、评分表、预注册的放行标准、评测运行说明。
**完成门槛：** 能在不知道模型身份的情况下复评关键场景，结果可由另一人按记录复现；评测集不再与开发/训练混用。

### P1：优先修复可复现的后端和任务遵循缺陷

目标：不把系统级 bug 交给模型训练掩盖。

1. 对最近报告中复现的记忆极性/并列事实问题，先补小而明确的验证用例，确保当前事实、历史版本、来源和短期上下文一致。
2. 对事实候选的“拒绝写入”记录拒绝原因，区分无证据、主体不符、时间冲突、解析失败，降低静默漏写的排查成本。
3. 把任务视角、代词/角色绑定、具体产物交付、最小步骤约束作为独立能力项，不要仅用路由符合率代表通过。
4. 继续分项记录分析 JSON 回退、回复回退、工具错误、数据库断言、语言质量；任何规则/提示调整都在开发集迭代，再用未参与调试的新场景检查。
5. 审查 `main.py` 的职责边界。仅在评测闭环稳定后，才拆分编排/分析/输出策略；避免把重构与行为修复同时混在一次对照里。

**完成门槛：** 可复现缺陷有回归覆盖；新场景未见同类硬失败；没有通过放宽来源校验来制造表面召回改善。

### P2：小批量、可追溯的 SFT/DPO 试验

目标：在后台硬约束之外，改善模型对语境、情绪和自然表达的判断。

1. 先从人工复核后的错误类型构建少量高质量样本，不直接启动 1,000 条批量合成。优先覆盖角色视角、引用/文学语境、反讽和混合情绪、具体任务交付、有依据的共情、工具失败时诚实表达。
2. 每条数据保留场景家族、来源/授权、目标回复理由、记忆证据、教师与提示版本、审核者和修改轨迹；对 SFT 目标与 DPO 偏好对分开审查。
3. 训练集与开发/保留集按场景家族隔离，做近重复和改写泄漏检查；评测样例及其改写不进入训练。
4. 先做一轮小型 LoRA SFT，与同一基线和纯提示改进对照；若没有稳定收益，不扩量。只有 SFT 后仍有明确偏好校准问题时，再做小规模 DPO。
5. 比较时固定同一模型底座、量化、推理参数、上下文、工具和 Avatar 后端；多次运行并报告分项分数、硬失败、降级、延迟和成本。

**完成门槛：** 独立保留集有可重复收益，关键失败无回退，训练/评测隔离审计通过。达到前不进入 OPD。

### P3：完成可演示的语音闭环

目标：把“有模块”推进到可衡量的端到端体验。

1. 确定最小演示范围：文本输入 → 回复 → TTS → 口型时间序列输出；先不要求 Live2D 美术和全功能实时交互。
2. 测 FunASR 的中文短句、噪声、专名、端点延迟和失败率；将可选依赖、模型下载及 CPU/GPU 占用写清楚。
3. 测 Edge-TTS 可用性、合成延迟、音频格式和失败降级；核实 TTS 音频到口型分析的实际格式链路，而非只测独立 lipsync 单元。
4. 定义渲染端输出协议（文本、音频文件/流、时间戳口型参数、情绪/策略元数据），提供最小接收端样例；再决定 Live2D 或 Godot。
5. 用固定中文句集评估口型元音分类和同步误差；在有数据前不宣称中文口型已达到实用准确度，也不优先加入声调映射。

**完成门槛：** 一台目标设备可按文档复现全链路；提供延迟、失败和同步误差记录，并清楚展示 ASR/TTS/模型不可用时的状态。

### P4：语义记忆、工具与产品化扩展

目标：在正确性和单用户边界明确后扩大能力。

- 用人工标注的 query–memory 相关/不相关对校准 embedding 阈值，分别测关键词、向量与混合召回的 precision/recall；验证错误记忆、历史版本、删除后索引的一致性。
- 增加隔离的工具集成评测：权限缺失、参数缺失、外部失败、重复调用、超时、撤销/删除与回复诚实性。不要让联网成功率替代对工具副作用的断言。
- 若目标转为多人试用，再单独设计账号、身份认证、数据隔离、权限、审计与备份/删除策略；当前工作台维持本机单用户定位。
- 完成文档一致性治理：更新 AGENTS/README 中已过时的当前状态；旧历史进度标注“历史快照”或迁入归档，设定单一当前路线图来源。

## 四、建议路线与决策点

### 推荐路线

**第 1 阶段：评测治理 → 第 2 阶段：后端缺陷修复 → 第 3 阶段：小批量训练对照 → 第 4 阶段：语音闭环演示。** 每阶段结束后依据门槛决定是否前进，而不是按日历自动扩大范围。

### 可选策略

| 策略 | 适用目标 | 优点 | 成本/风险 | 建议 |
|---|---|---|---|---|
| A. 质量优先 | 大创结题可信度、系统可靠性 | 先补人工验收和评测隔离，避免训练数据污染 | 前期可见的新功能较少 | **推荐作为主线** |
| B. 体验优先 | 尽快做展演 Demo | 并行补 TTS/ASR/渲染协议，展示完整交互 | 后端行为仍有已知缺陷，容易把模块串通误当体验成熟 | 仅做范围很小的演示原型，并标出限制 |
| C. 训练优先 | 研究模型适配效果 | 能尽早验证本地 LoRA 技术链路 | 评测未冻结时结果不可信，容易训练泄漏、归因混乱 | 暂缓，完成 P0 后再启动小实验 |
| D. 平台优先 | 多人长期使用/部署 | 可规划认证、隔离、运维和工具权限 | 当前单用户原型与目标不同，范围会快速扩大 | 只有目标明确转向多人产品时启动 |

## 五、近期可执行清单

1. 由项目成员人工复核 12 条新场景及前序关键失败，形成裁决记录。
2. 审核并清理 100 条候选集，保留已暴露样例为回归集；补写独立开发集/保留集规则与放行标准。
3. 选出不超过 3 类最高优先缺陷，分别建立新场景开发样例和后台断言；修复一类、回归一类，避免同时改提示、规则和训练。
4. 修复 README、AGENTS 与 `docs/项目进度.md` 的状态冲突，明确“文本后端已评估、语音/渲染尚待端到端验收”。
5. P0/P1 达到门槛后，做小批量 SFT 可行性实验；另行决策是否启动语音 Demo。
