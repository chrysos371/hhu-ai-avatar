# 回复侧事实来源、写作角色与草稿引用

本模块的角色是“这封消息由谁写给谁”，不是数字人人设卡或模型身份。实现位于 `src/avatar/brain/reply_context.py`，由 `Avatar._assemble_reply_messages` 统一调用；角色馆与QQ的ConversationService也经过同一入口。没有扩大共享记忆、管理权限或外部动作权限。

## 数据边界

- 当前窗口内的用户原话是任务来源，不能自动等同已确认用户画像。用户最新纠正优先；长期画像仍经既有supported_fact/来源证据校验。
- 发信角色只取用户明确声明、代理对象或身份切换，并保留来源窗口ID和原文片段；不从助手的自称推断。
- 事实核对、重新起草等任务中隔离旧助手消息；明确或隐式引用旧稿的编辑保留原稿。一般闲聊保持原有历史。原消息数据库和人工审计不删除、不改写。
- 角色状态每轮从有边界的历史窗口重建，适用于QQ每轮重建实例；不持久写入角色关系或用户画像。

`reply_context_enabled=False` 是回归对照开关；关闭后不启用本模块的上下文隔离、角色校验或确定性询问生成。它不会关闭原有现实边界或记忆证据检查。

## 有界生成与校验

对于用户明确给出的短询问、明确的申请/提交者身份及正文交付要求，可以直接生成“您好，请问{用户问题}？”。问题必须连续来自用户原话，未知接收人不补头衔；不做审批、发送或资料补全。草稿编辑、JSON/代码等特殊格式、取消询问、有待保留占位等不走这条路径。认知分析仍可能调用模型，只有正文不需要模型生成。

其他回复仍由模型生成。只对可识别的写作角色做窄范围检查：

- 代拟第一人称却把本人写成“我姐姐”等；尊重明确指定的第三人称。
- 申请者反过来审核接收者的申请。
- 缺乏用户肯定来源的“已提交/已准备”等完成状态；提问、否定、引述不能作为完成证据。
- 模型自行补出的部分组织身份。

检查发现问题时，最多从用户证据重生成一次，不把被拒绝的候选放回事实历史。仍失败则明确标记不能作为可靠可发送正文，不假装已经成功。这个检查器不是完整语义裁判，不能宣称所有未知身份、材料名或不当断言都已识别。

## 流式与可观察性

整合版对于本模块处理的任务会缓冲流式候选，校验完成后再交付；普通闲聊保留原有流式行为。旧主目录分支没有流式API，保留其同步接口，没有移植其他不相关上游功能。

每轮结果及统一trace增加：

- `reply_context`：模式、来源数量、隔离/保留的助手条数、角色有无来源等。不写入原文或实际身份值。
- `context_check`：初始与剩余问题、是否尝试重生成、是否成功、是否阻止正文，以及确定性询问的规则和来源ID。
- `generation_mode=grounded_user_inquiry`：正文由用户问题直接生成；不能计为底模或LoRA能力提升。

规则危机响应、隐私边界、工具与提醒执行都不进入写作重生成。额外生成和任务缓冲可能增加写作延迟，应在回归中单独记录。

## 限制

当前是基于显式中文表达的有界规则，不是通用角色理解器。超出窗口或无法可靠识别的主体保持未知，跨话题关系和长期经历不由此推断。简单模式可能漏检或误判，须同时检查实际交付、失败拦截与正常改稿，不能只看机械测试通过。

测试覆盖来源隔离、上下文重建、明确/隐式草稿引用、角色/人称继承、问句与否定来源、一次重生成上限、失败标记、流式不泄露候选和角色馆入口。真实模型结果另见本轮后台回归报告，不以单元测试代替效果验收。


本轮最终补充：无明确角色的纯格式收尾按草稿引用保留刚推导出的内容，无角色旧稿编辑不额外加入角色提示。完整回归与复测见 `docs/2026-11-11-后台事实角色与草稿修复回归.md`；不能把保留草稿理解为把助手文本认定为真实事实。
