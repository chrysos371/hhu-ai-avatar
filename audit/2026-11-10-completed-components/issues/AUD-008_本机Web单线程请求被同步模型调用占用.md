# AUD-008 · 本机 Web 单线程请求被同步模型/工具调用占用

- **等级：** P2 · 中（可用性与提醒时效）
- **类别：** Web 请求调度 / 超时
- **状态：** 静态服务调用路径确认；未做压力或延迟测量
- **置信度：** 高

## 摘要

工作台使用标准库 `HTTPServer`（单请求服务循环）。`POST /api/chat` 在该服务线程内同步执行 `Avatar.respond()`；普通 LLM 调用没有显式应用层 timeout，联网代理则在同步调用中运行异步工具流程。慢模型或慢网络请求会占住唯一服务线程，期间记忆/提醒/state API 不能被处理，浏览器的 15 秒提醒轮询也只能排队。

## 证据

- `src/avatar/web.py:7` 导入 `HTTPServer`，`create_server()` 在 `:152-162` 创建单线程服务。
- `src/avatar/web.py:76-93` 在请求处理函数内直接调用 `avatar.respond()`，没有将耗时任务交给 worker。
- `src/avatar/main.py:404-413` 同步调用 LLM 回复；异常捕获没有应用级超时控制。
- `src/avatar/brain/llm.py:29-44` 普通 `chat()` 创建请求时没有传 `timeout`；分析与工具请求另有超时配置，但普通对话没有显式约束。
- `src/avatar/main.py:398-403` 联网回合同步调用 `WebAgent.run()`，其内部 `asyncio.run()` 会等整个工具流程结束后才返回。
- `src/avatar/web_ui.py:31-32` 前端每 15 秒触发一次提醒轮询，但轮询请求与所有其他 API 共用同一个服务线程。

## 影响

当模型服务响应缓慢、默认 SDK 超时很长或联网工具遇到延迟时，记忆表格刷新、提醒状态变更和到期提醒检查都会等待当前对话请求结束。用户可能看到页面短暂无响应，提醒显示晚于计划时间。当前设计是本机单用户，因此问题主要是响应时延和提醒时效，而非并发吞吐量。

## 建议

1. 为普通 LLM 请求显式设置可配置的超时，返回可区分的超时/降级状态。
2. 将聊天与提醒轮询/管理 API 的耗时工作隔离；如改用线程服务，需同步保护共享 `EmotionEngine`、session short-term 状态及 SQLite 写入。
3. 为前端轮询增加单飞/退避，避免慢请求期间叠加排队。
4. 如果保留单线程作为 MVP 取舍，在界面说明聊天期间提醒轮询可能延迟，并避免宣称准时推送。

## 验收建议

- 人为延迟模型响应时，工作台仍可读取/管理提醒，或明确展示请求被占用。
- 到期提醒的最长显示延迟有目标值，且以端到端测量验证。
- 超时后聊天状态能恢复，不留下卡住的提交按钮或重复请求。
